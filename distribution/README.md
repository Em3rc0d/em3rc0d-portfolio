# DISTRIBUTION

This directory stores the **public reputation operating system** that sits downstream from THE BUILD ROOM.

The portfolio remains the source of truth. Distribution does not become a second place where stronger claims are invented.

## Purpose

```text
SYSTEM / EVIDENCE / NOTE
        ↓
DISTRIBUTION OBJECT
        ↓
PUBLIC POST
        ↓
PORTFOLIO INSPECTION
        ↓
CONVERSATION
        ↓
LEARNING
```

## Source rule

A technical post must point back to one or more public-authorized objects:

- system case;
- evidence record;
- built/verified note;
- public professional record;
- public source repository.

The post may simplify language. It may not strengthen the claim.

## Object state

```text
CANDIDATE

```

## Writing voice

The public notebook should sound like a software developer explaining a system boundary he actually had to reason about.

Prefer:

- specific distinctions;
- concrete state names;
- small architecture models;
- implementation tradeoffs;
- failure behavior;
- explicit uncertainty;
- bounded professional lessons.

Avoid:

- influencer cadence;
- fake certainty;
- motivational filler;
- inflated titles;
- generic tutorial content disconnected from real work;
- "hot takes" written only to provoke comments.

## Visual language

Distribution extends THE BUILD ROOM:

```text
CARBON / GRAPHITE
PAPER
RED ACTIVATION
TECHNICAL MONO LABELS
STATE / FLOW / PROOF DIAGRAMS
```

Primary social canvas: `1080 × 1350`.

A graphic should explain the engineering thought even if the caption is not visible.

## Review rule

The first six-post launch cycle is intentionally manual.

Do not automate generation, approval, or publishing until we have enough real distribution evidence to know which parts of the process are stable.

The first automation candidate should be **source extraction / draft assistance**, not autonomous publishing.
