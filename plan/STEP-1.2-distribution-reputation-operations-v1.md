# 3. Audience

## Primary

People responsible for software or operational systems where the problem is messy before it is technical:

- technical leads and engineering managers;
- founders / operators with custom software needs;
- teams recovering or extending existing systems;
- people evaluating full-stack / systems / applied-AI engineering ability.

## Secondary

- recruiters and hiring managers for software-development roles;
- engineers who may become peers, referrers, collaborators or future clients.

The content should remain technically credible to engineers while still understandable to a non-specialist operator who owns the problem.

---

# 4. Source-of-truth rule

Distribution is downstream from THE BUILD ROOM.

Every technical post must begin from at least one public-authorized source object:

```text
SYSTEM CASE
EVIDENCE RECORD
BUILT / VERIFIED NOTE
PUBLIC PROFESSIONAL RECORD
PUBLIC SOURCE REPOSITORY
```

A distribution draft may simplify a concept for readability, but it may not strengthen the underlying claim.

The chain is:

```text
SOURCE OBJECT
    ↓
SUPPORTED CLAIM
    ↓
PUBLIC POST
    ↓
PORTFOLIO BRIDGE
```

If the source is silent, the post stays silent.

---

# 5. Editorial territories

The launch mix is intentionally narrow.

```text
SYSTEM THINKING       30%
BUILD / IMPLEMENT     25%
RECOVERY / FAILURE    20%
APPLIED AI / TRUTH    15%
EVIDENCE / PRACTICE   10%
```

These are not rigid quotas. They prevent the feed from collapsing into only one identity such as "AI developer" or "React developer."

Professional-depth material is a context that may appear inside SYSTEM THINKING, BUILD, RECOVERY or EVIDENCE rather than becoming a separate corporate-content category.

---

# 6. Content formats

## A. Engineering Note

A native text post built around one technical distinction.

Contract:

```text
HOOK / TENSION
    ↓
THE SHORTCUT OR FAILURE MODE
    ↓
THE BOUNDARY / MODEL
    ↓
WHY IT MATTERS
    ↓
OPTIONAL INSPECTION ROUTE
```

Target length: roughly 180–320 words when the idea supports it. No padding to hit a word count.

## B. Proof Walkthrough

A post plus one visual artifact showing a bounded engineering path.

Examples:

- state transition;
- source → model → decision;
- browser → API → persistence → realtime;
- claim → proof → limitation.

The visual is explanatory, not decorative.

## C. Builder / Professional Record

A post about a real engineering constraint or implementation responsibility.

It must preserve confidentiality and ownership boundaries.

Do not expose private screenshots, repository coordinates, employer/client identifiers or operational/security details merely to make the post feel more impressive.

# 8. Publishing contract

Every post must pass these checks before publishing:

```text
1. Does the first line contain a real idea or tension?
2. Can the post stand alone without clicking a link?
3. Is at least one concrete system behavior or model present?
4. Does the wording stay inside the source's claim ceiling?
5. Is the language recognizably Eduardo rather than generic creator copy?
6. Is the CTA optional rather than withholding the useful part?
7. If a visual exists, does it explain rather than decorate?
```

Forbidden launch patterns:

- "5 lessons I learned about React" without a real source object;
- fake controversy;
- engagement bait;
- inspirational filler;
- invented client outcomes;
- "AI will change everything" posts;
- fake screenshots or fake telemetry;
- pretending an archived technical challenge is production adoption;
- leaking professional/private material.

---

# 9. Link / bridge contract

The native post must deliver the insight in full.

When an inspectable route adds real value, prepare one bridge separately:

```text
PORTFOLIO ROUTE
or
PUBLIC SOURCE ROUTE
```

The bridge may be placed in the post or first comment depending on the publishing context. This is an editorial choice, not a claim that one placement is algorithmically superior.

The CTA language should be low-pressure:

- "I documented the full boundary here."
- "The evidence record is inspectable here."
- "I kept the full system path in THE BUILD ROOM."

Avoid:

- "Click here before it disappears";
- "Comment YES and I will send it";
- artificial scarcity;
- generic "Thoughts?" appended to every post.

- diagrams before stock photography;
- no random car imagery outside AutoPulse relevance;
- no fake terminal/code screenshots;
- no private professional screenshots;
- no tiny code walls;
- visible source/boundary label when a graphic reconstructs a system model.

---

# 11. Conversation contract

Publishing is not finished when the post is live.

For each post:

1. remain available after publishing when practical;
2. answer technical questions with the same evidence discipline as the portfolio;
3. distinguish implementation fact from opinion or open research;
4. do not manufacture debate for reach;
5. capture good questions as future content candidates;
6. move a conversation to DM only when there is a real reason to continue privately.

A strong comment can become a new NOTE candidate only after its claim is recovered and checked.

---

# 12. Measurement model

Track what the platform actually exposes and what Eduardo can observe directly.

Core measurements:

```text
IMPRESSIONS / REACH         context only
REACTIONS                   weak signal
COMMENTS                    quantity
SUBSTANTIVE COMMENTS        stronger qualitative signal
REPOSTS / SAVES             when exposed
PROFILE ACTIVITY            when attributable/observable
PORTFOLIO CLICKS            only if instrumented
QUALIFIED DMs               manual count
QUALIFIED CONVERSATIONS     manual count
OPPORTUNITIES / REFERRALS   manual count
```

Never fabricate an unavailable metric.

The principal review question after each six-post cycle is:

> Which topics caused the right people to inspect, ask, reply or continue the conversation?

# 13. Distribution object lifecycle

Each post moves through explicit states:

```text
CANDIDATE
   ↓
SOURCE_LOCKED
   ↓
DRAFTED
   ↓
VISUAL_READY
   ↓
APPROVED
   ↓
PUBLISHED
   ↓
MEASURED
   ↓
LEARNED
```

A draft is not a published claim.

A published post is not automatically a successful distribution object.

---

# 14. Launch gate

STEP 1.2A — Distribution Foundation closes when:

- the distribution repository structure exists;
- the source/claim/publishing contract is documented;
- six launch posts are source-locked and publish-ready;
- each launch post has a portfolio/source bridge;
- each launch post has a visual brief;
- an analytics ledger exists;
- no launch content exceeds its source evidence.

Publishing itself begins only after this foundation is accepted.

# 15. What follows

After the first six posts:

```text
PUBLISH
  ↓
MEASURE
  ↓
REVIEW QUALIFIED RESPONSE
  ↓
REFINE TERRITORY / FORMAT / HOOK
  ↓
SECOND SIX-POST CYCLE
```

Only after repeated manual cycles produce a stable contract should automated generation or scheduling become authoritative.

Automation must inherit the editorial/evidence rules; it must not replace them.
